# EDAM-S3-POLICY-AUDIT — MinIO IAM Policy Audit Report

**Task:** EDAM-S3-POLICY-AUDIT (Sprint-3 Phase P1, after S3-SoD + SOD-F1/B2).
**Date:** 2026-06-04.
**Subject:** the three committed least-privilege MinIO IAM policies in
[`deploy/compose/minio/policies/`](../deploy/compose/minio/policies):
`edam-writer-policy.json`, `edam-reader-policy.json`, `edam-retention-admin-policy.json`.
**Scope:** export + audit the policy definitions, produce the role/action permission
matrix, verify consistency with the WORM contracts and the Option-B2 narrowing, and
live-validate store-enforced behavior with raw clients. **Not in scope:** H5 (the
comprehensive live 403 enforcement suite), S3-REVAL, any new hardening.

## 1. Determination

**The committed policies are internally consistent, least-privilege, and fully
aligned with the WORM separation-of-duties model (S-6/S-7) and the Option-B2 writer
contract.** The static audit reports **0 violations**; the committed policies are
**semantically identical** to the live in-store policies; and raw-client live
validation confirms the store enforces the intended allow/deny matrix. No gaps were
found that contradict the policy intent. Residual items (Section 8) are deferred work
for H5 / S3-REVAL / production sign-off, not defects in these policies.

## 2. Methodology

1. **Static audit (offline, deterministic):** `conformance/scripts/s3-policy-audit.ts`
   parses the three committed JSON policies, computes the effective effect of each
   action (explicit **Deny overrides Allow**; ungranted ⇒ implicit deny), and asserts
   the SoD model. Gated by `conformance/test/s3-policy-audit.test.ts` in the default
   `npm test` (no MinIO) — a durable regression guard against future policy drift.
2. **Live export + drift check:** `mc admin policy info` exported each in-store policy;
   each is semantically identical to its committed file (only MinIO's cosmetic
   envelope/ordering differ). Exports archived under `docs/evidence/policy-audit/`.
3. **Live store-enforced validation:** raw `mc` per-role aliases + the `minio` SDK
   (gated integration suite) exercised the allow/deny matrix against a real MinIO —
   **no adapter shortcuts**. See `docs/evidence/policy-audit/live-validation-matrix.md`.

## 4. Per-role detail (allow / explicit-deny / scope)

### writer (`edam-writer`) — Domain B, append-only producer
- **Allowed (exactly):** `s3:PutObject`, `s3:GetObject` (the latter for the adapter's
  `statObject`/HeadObject no-overwrite pre-check).
- **Explicit Deny:** `DeleteObject`, `DeleteObjectVersion`, `PutObjectRetention`,
  `PutObjectLegalHold`, `BypassGovernanceRetention`, `PutBucketPolicy`,
  `PutBucketObjectLockConfiguration`, `PutBucketVersioning`.
- **Object scope:** `arn:aws:s3:::edam-evidence/*`. **Bucket scope:** (deny only).
  **Admin scope:** none.

### reader (`edam-reader`) — read / export
- **Allowed:** `GetObject`, `GetObjectRetention`, `GetObjectLegalHold` (objects);
  `ListBucket`, `GetBucketVersioning`, `GetBucketObjectLockConfiguration` (bucket reads).
- **Explicit Deny:** all writes/deletes/retention/legal-hold puts + bucket config writes
  + `BypassGovernanceRetention`.
- **Scope:** object + bucket reads on `edam-evidence` only. **Admin scope:** none.

### retention-admin (`edam-retention-admin`) — Domain C, custodian
- **Allowed:** `Get/PutObjectRetention`, `Get/PutObjectLegalHold`, `GetObject` (objects);
  `ListBucket`, `Get/PutBucketVersioning`, `Get/PutBucketObjectLockConfiguration`
  (bucket bootstrap, used by the adapter `ensureBucket()` on the retention-admin client).
- **Explicit Deny:** `PutObject` (no content write), `DeleteObject`,
  `DeleteObjectVersion`, `BypassGovernanceRetention`, `PutBucketPolicy`.
- **Scope:** object + bucket on `edam-evidence` only. **Admin scope:** none.

All policies use **explicit Deny** (defense-in-depth: the boundary holds even if a
broad Allow were ever attached) and reference **only** `arn:aws:s3:::edam-evidence`
and `…/*` — no cross-bucket access, no `admin:*` / IAM-management actions.

## 5. Consistency with the WORM contracts + implementation

| Contract / code | Policy alignment |
|---|---|
| `WormWriter` (Domain B; B2 — `WriterPutOptions` cannot express retention/hold) | writer policy denies `PutObjectRetention`/`PutObjectLegalHold` and grants only `PutObject`+`GetObject`. The adapter writer path (`MinioWormStore.putImmutable` on `writerClient`) issues **only** `putObject` — so its permission set matches its behavior exactly. |
| `WormReader` (get/list/headObjectLock) | reader policy grants exactly the object reads + lock-metadata reads + bucket reads those methods require; denies all mutation. |
| `WormRetentionAdmin` (extendRetention / placeLegalHold / liftLegalHold / deleteExpired) | retention-admin policy grants `Put/GetObjectRetention` + `Put/GetObjectLegalHold`. **Lawful expiry deletion** (`deleteExpired`) is **NOT** a standing grant — `DeleteObject`/`DeleteObjectVersion` are denied; deletion is dual-controlled (S-2/S-8) and out of scope of any single role. |
| `MinioWormStore` client routing | `writerClient` → writer policy (put only); `readerClient` → reader policy; `retentionAdminClient` → retention-admin policy (incl. `ensureBucket()` bucket-config writes). Verified: `writerClient` never reaches a denied API. |
| Option B2 narrowing | the writer cannot set retention/hold in the type **and** is denied at the store — type-level and store-level enforcement agree. |

## 7. Live validation summary

Raw-client validation against a real MinIO confirmed every cell of the matrix is
**store-enforced**. The authoritative signal per cell is the store response + actual
object/lock state (the `mc` CLI exit code is unreliable for `legalhold`/`retention`/
`cp` — documented in the evidence). The gated `minio` SDK integration suite
(28 passed) independently asserts the same denials with `expect(...).rejects`,
including the B2 proof that the adapter writer path issues only `putObject`. Full
detail: `docs/evidence/policy-audit/live-validation-matrix.md`.

## 8. Gap analysis (residual — deferred, not policy defects)

1. **retention-admin holds bucket lock-config + versioning writes**
   (`Put/PutBucketObjectLockConfiguration`, `PutBucketVersioning`) — required by the
   adapter's `ensureBucket()` bootstrap on the retention-admin client. It cannot
   retroactively weaken COMPLIANCE-locked objects, but it can change the bucket
   **default** for future writes. *Recommendation:* in production, split bucket
   bootstrap into a one-time provisioning identity and put lock-config changes under
   dual-control (S-8). Tracked for production sign-off, not P1.
2. **No live 403 enforcement suite across the full action surface** — this audit
   spot-validates the key cells; the comprehensive, CI-gated live 403 suite is **H5**.
3. **mc CLI exit-code unreliability** — operational caveat for any shell tooling built
   on `mc` (`legalhold`/`retention`/`cp`); prefer the SDK / store response, not `$?`.
4. **Out of P1 scope (production):** mTLS (S-4), IP allowlist (S-5), dual-control
   (S-8), immutable backups (S-10), DR (S-11).

## 9. Recommendations

- **Keep the static audit gate** (`s3-policy-audit.test.ts`) as a required check so any
  future edit to the committed policies must keep the SoD model intact.
- Proceed to **H5** for the comprehensive live store-level 403 enforcement suite, then
  **S3-REVAL** for end-to-end re-validation under per-role credentials.
- For production, address gap (1) (bootstrap/dual-control separation) and the S-4/S-5/
  S-8/S-10/S-11 items in the Production Security Sign-Off track.
